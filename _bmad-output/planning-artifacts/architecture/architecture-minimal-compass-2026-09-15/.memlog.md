- (constraint) ADOPTED: single Gradle module, no DI framework, no persistence layer beyond SharedPreferences. Observed across 25 source files; nothing suggests this is under review.
- (decision) ADOPTED paradigm: unidirectional flow, hardware -> Flow -> single ViewModel -> StateFlow -> Compose. Binds: every new sensor-derived value. Prevents: a second source of truth for heading/tilt appearing beside CompassViewModel.
- (decision) ADOPTED layering: sensor/ owns hardware and raw derivation; viewmodel/ owns state and policy; ui/ renders; util/ is pure and framework-free; widget/ is isolated and shares no runtime state with the app. Binds: file placement for new work. Prevents: hardware access leaking into composables.
- (decision) ADOPTED sensor lifetime: stateIn + WhileSubscribed(5s), driven by the UI via repeatOnLifecycle(STARTED). Binds: any new hardware subscription. Prevents: sensors held while backgrounded - the app's largest historical battery bug.
- (decision) ADOPTED: every tunable number lives in Constants.kt, grouped by subsystem. Binds: thresholds, durations, filter coefficients, proportions. Prevents: the same threshold drifting apart at two call sites.
- (constraint) ADOPTED privacy invariant: position is never persisted or transmitted. DeclinationRepository returns only the derived angle; prefs hold only last_declination_deg + timestamp. Telemetry logs enums only. This is a Play Data Safety commitment, not a preference.
- (decision) ADOPTED: red is reserved for north alone; green (levelOk) means correct/on-target. Binds: every new UI element. Prevents: two red marks meaning different directions.
- (constraint) ADOPTED: the widget holds no live data by design - a heading it cannot keep fresh is a guess presented as fact.
- (event) Brownfield sweep complete: 25 Kotlin sources, two screens, one widget, shipped v1.0.0.
- (decision) Any decision with a threshold, hysteresis or dwell is a pure class in sensor/ taking an injectable clock, unit-tested, consumed by the ViewModel. Binds: every mode gate and every debounce. Prevents: the same shape being written four different ways in four layers, and untestable timing logic - the horizon dead zone shipped frozen because a LaunchedEffect keyed on a live float never completes, which a fake-clock unit test catches immediately.
- (decision) State that changes hardware behaviour lives in the ViewModel. Composables hold presentation state only. Binds: anything deciding when a sensor or the camera is open. Prevents: camera lifecycle being decided in two places, which is how a stale PreviewView observer could latch AR hidden.
- (constraint) DEBT, recorded deliberately: the two decisions above are not yet met by the code. CardinalOverlay holds the horizon dead zone inline; CompassScreen holds the camera warm debounce, arStreaming and warmingCamera. The spine states the target, not the present.
- (question) Open: does the ARCore Phase 2 direction (TODO hooks in MainActivity, CompassViewModel, SensorRepository, manifest, gradle) stay a committed direction or get deferred? It currently shapes five files without being decided.
- (direction) ARCore stays a COMMITTED direction, not a deferred one. The five TODO hook sites (MainActivity, CompassViewModel, SensorRepository, AndroidManifest camera.ar feature, build.gradle.kts) are the agreed integration points; future AR work builds toward them rather than around them. CameraX remains the shipping implementation until ARCore lands.
- (decision) New runtime dependencies require a stated justification against what they replace and what they cost in APK size and startup. Explicitly out: DI framework, navigation library, persistence layer beyond SharedPreferences. Binds: every addition to libs.versions.toml. Prevents: a lean app eroding one reasonable-looking library at a time.
- (constraint) Noted tension, resolved: ARCore is itself a heavy dependency and is pre-justified by the committed direction above. It is the named exception to the dependency rule, not a counterexample to it.
